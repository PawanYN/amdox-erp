**Breakdown of the remaining 5 items — problem, why, how, outcome:**

1. **k6 load test (2,000 VUs, 10-min steady state)** — _Load testing._
   Nobody has ever thrown concurrent traffic at this API; every perf claim so
   far (N+1 fix, 8 indexes) was validated one query at a time with
   `EXPLAIN ANALYZE`, not under simultaneous load, so the actual req/s
   ceiling and first-to-fail endpoint are unknown. Needed because this ERP's
   modules all share one Postgres connection pool — concurrent users compete
   for it, and "works for one user" isn't the same claim as "works for 2,000."
   Implementation: a k6 script under `testing/load/` that logs in once via
   the Keycloak token endpoint, then hits real hot paths (invoice list,
   `POST /finance/ap/payment-runs`, a reporting endpoint) with a ramp to
   2,000 VUs held for 10 minutes, results logged to
   `testing/K6_LOAD_TEST_LOG.md` the same way the query-optimisation audit
   was. Outcome: concrete p95 latency / error-rate / max-RPS numbers and the
   exact query that degrades first — the thing that tells you whether items
   2 and 3 below are actually needed or premature.
2. **Redis cache gaps** — _Query caching._
   `RedisService` already exists and is wired in, but only for BullMQ queues
   and rate-limit storage — never as a cache, so every BI/reporting read hits
   Postgres fresh even for near-static data. Needed so repeated reads of
   reference-ish data (vendor/product lists, BI aggregates) stop competing
   with writes for DB connections under load. Implementation: a thin
   `CacheService` wrapper around `RedisService` with tenant-scoped keys and
   TTLs, applied to the highest-traffic read endpoints, invalidated on
   write. Outcome: lower p95 on dashboard-heavy pages and fewer Postgres
   round-trips for data that doesn't change every request.
3. **Postgres read-replica strategy for BI/reporting** — _Read scaling._
   Reporting queries (large date-range scans over `Invoice`, `JournalEntry`,
   `StockMovement`) run on the same primary instance that handles live
   transactional writes, so a heavy report can starve payment-run/payroll
   writes of IO. Needed because reporting reads tolerate a few seconds of
   staleness — a textbook case for offloading to a replica instead of
   competing with the write path finance depends on for correctness.
   Implementation: a written strategy (`docs/postgres-read-replica-strategy.md`)
   covering a streaming replica in `docker-compose.prod.yml`, a
   replica-pointed Prisma client for the BI module only, and a fallback to
   primary if the replica connection drops. Outcome: a reviewable plan the
   team can build from without re-deriving the architecture — doc only in
   this pass, no infra stood up.
4. **React frontend Lighthouse score ≥ 90** — _Frontend performance._
